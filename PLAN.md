# PLAN.md — PoC → Production Hardening

Status: **implemented** — 161 unit tests + 9-assertion e2e suite green on python3.14 (baseline was 140 @ cad2475). See "Final verification" at the bottom.

## Governing design rules

1. This is a PoC being demoed for real feature potential, then productionized.
   Optimize for: correctness of the deterministic layers, no wasted LLM spend,
   honest telemetry, one central LLM provider manager, pluggable providers.
2. Unchanged by explicit user instruction: score thresholds (75% pass, 70%
   per-question answered, 25% abort, 25–70% follow-up band), time limits per
   question type, question count scaling (2–8), the 80/20 diff/standards ratio.
3. "No commit if there are serious issues" = the existing credential gate,
   run FIRST (fail fast, before any prompt), plus a security-relevant commit
   must get its security question — that already exists and is kept.

## Workstreams

### W1 — Gate ordering (fail fast)  [cli.py]
Move the credential gate BEFORE the coding-standards fix/proceed prompt.
Behavior change: a staged live credential now blocks before the user is ever
prompted; no standards report printed on that path; no LLM prefetch started.
The gate's own output (unstage hints, gitignore callout) unchanged.

### W2 — LLM Provider Manager (one central module)  [NEW llm_manager.py]
Current state: provider/model/base-url/key resolution is spread across
api_utils.get_base_url / get_model / load_nous_api_key + a gsk_ sniff +
UNDERSTANDING_AGENT_PROVIDER + per-caller `_call_groq` shims + a default model
that is a typo (`qwen/qwen3.8-27b`) and a README that says something else.
Goal: `llm_manager.py` exposes a single `LLMManager` — `chat(messages, **kw)`
-> (status, body) with provider presets (nous, groq, openai, openrouter,
together, ollama/local, custom), model/base_url/key resolved from ONE env
namespace per provider:

    UNDERSTANDING_AGENT_PROVIDER   (preset name; default: nous)
    UNDERSTANDING_AGENT_MODEL      (model id, any preset)
    UNDERSTANDING_AGENT_BASE_URL   (override; enables ANY OpenAI-compatible)
    UNDERSTANDING_AGENT_API_KEY    (key; else preset-specific default var)

Presets carry: default base_url, default model (verified ids), default key env
var. Legacy vars (NOUS_API_KEY, NOUS_MODEL, NOUS_BASE_URL, GROQ_API_KEY,
GROQ_MODEL, GROQ_BASE_URL) keep working through a compat layer so no existing
user setup breaks and tests that patch api_utils symbols keep passing.
api_utils keeps `extract_json`, `load_nous_api_key` (delegates to manager),
retry logic; `_nous_request_once` delegates to manager.
Fix default Groq model to a real production id: `llama-3.3-70b-versatile`.

### W3 — No wasted LLM calls  [cli.py, question_generator.py]

- If user chooses "fix violations", zero LLM calls are made (currently the
  bg thread may already have called summary+questions).
- Gate blocks → zero LLM calls (already true once W1 lands).
- Same-diff retry uses cached questions (already true; kept).
- Kill the dead duplicate-append bug in `_ensure_standards_questions`
  (question_generator.py:692-695); make the fallback fill loop actually
  iterate over candidates.

### W4 — LLM unreachable ⇒ fallback questions + commit marked not verified
[cli.py, session payloads]
When summary/questions/evaluation run on fallback (no key or API error) with
fail-open mode, the commit may proceed, but:
- The session payload gains `"verification": "llm-unverified"` (vs
  `"llm-verified"`) and `status` remains PASSED/FAILED by score.
- Terminal prints a one-line warning: "⚠ LLM unreachable — answers not
  LLM-evaluated; commit marked UNVERIFIED in dashboard".
- The 76-score fail-open quirk (answer_evaluator.py:98-100) stays for
  pass/abort behavior (thresholds unchanged) but its evaluation text and the
  session now say "unverified".
- Coding-standards-violation questions generated by the deterministic
  builder (`_build_proper_standard_question`) remain valid questions; they
  are marked `is_fallback: True` — they were never LLM questions. No change.
