# Understanding Agent — System Overview (non-technical)

*What it is, why it exists, and what actually happens — in plain language.
Technical detail lives in [ARCHITECTURE.md](ARCHITECTURE.md).*

## The problem

Code review can verify that a change is *correct*, but it cannot verify that
the person who wrote the change *understands* it. This gap got dramatically
wider when AI coding assistants entered the picture: code now arrives fast,
looks plausible, and is sometimes not understood by the person committing it.
Rubber-stamped reviews and "it worked on my machine" merges are the symptom.

Understanding Agent closes that gap at the one moment it can be closed
cheaply: **the commit**. Before a change becomes permanent git history, the
author is asked to explain it — out loud, in their own words — and the
explanation is scored.

## What it is, in one paragraph

A pre-commit hook (a script git runs automatically before finishing a
commit). When you commit, it:

1. **Hard-blocks live credentials** — API keys, passwords, key files staged
   by mistake never reach history. This part is fully deterministic; no AI
   is involved in the decision.
2. **Audits coding standards** — a deterministic report of violations in the
   changed lines, which the author can fix or acknowledge.
3. **Asks the author questions about their own change** — generated by an
   LLM from the actual diff ("what happens if the token is missing?", "why
   does this function call validate before insert?"). The author answers by
   typing or speaking. Answers are scored by a separate judge model.
4. **Records everything** — locally on the developer's machine, and
   (optionally, for teams) in a central database that becomes proof the
   commit was understood.

A commit passes when the author demonstrates understanding (score > 75%),
and a bad answer on one question gets one focused follow-up before anything
fails. A wrong or empty answer below 25% aborts the commit — you review and
try again.

## What it deliberately never does

- **Never lets AI decide a security block.** The credential gate is pure
  pattern-matching code. An LLM reading attacker-controlled diff text is an
  injection risk, so AI findings are advisory only — they inform questions,
  they can never block or unblock anything.
- **Never blocks a commit because the network is down.** No AI key
  configured, API unreachable, central server offline — the hook degrades to
  deterministic offline questions, marks the session "unverified" honestly,
  and lets the commit proceed (fail-open). The alternative (fail-closed)
  was rejected because a flaky API must never take a team's commit flow
  hostage.
- **Never judges language or spelling.** Answers can mix languages (Hindi +
  English, anything); only concept coverage is scored. Dictation glitches
  get a "say it again" prompt instead of a wrong score.
- **Never sends your code somewhere you didn't configure.** Diff content goes
  only to the AI provider you configure (Nous, Groq, OpenAI, OpenRouter,
  Together, Ollama — even a fully local model). Telemetry/central sync is
  opt-in and sends session records (questions, answers, scores), not raw
  diffs.
- **Never punishes honest "I don't know" with silent data** — a failed
  attempt is recorded as failed; nothing is silently marked as verified.

## The three layers

| Layer | Question it answers | Who feels it |
|---|---|---|
| Credential gate | "Is a live secret about to enter history?" | Everyone, instantly — deterministic, no prompts |
| Oral defense | "Does the author understand their own change?" | The author, ~1–3 minutes per commit |
| Central ledger (optional, teams) | "Which commits were defended — and which bypassed the hook?" | CI and team leads; a pushed commit with no defense record is flagged automatically |

## Deployment shapes

- **Solo developer**: install the hook, set an LLM provider key in `.env`.
  Sessions live in a local database. No central anything. Free, private.
- **Team**: additionally run the central ledger service (a small FastAPI +
  Postgres app, Docker provided). Hooks sync sessions to it — offline
  commits queue locally and sync later, never blocking the commit. CI runs a
  proof-of-defense check: every commit in a PR must have a recorded defense.
  `--no-verify` skippers, fresh clones without hooks, and AI agents are all
  caught the same way: their commits simply have no record.

## AI agents get special treatment

Agents (Codex, Claude CLI, etc.) commit via git, so the hook fires — but no
human is there to answer questions. Instead of failing, the hook records the
commit as **agent-unverified** and lets it through; the team's CI policy can
then require a human review on top. Agents are treated as a new class of
"unverified but recorded" actor, not as cheaters.

## What teams get out of it

- Fewer "I don't know why this works" commits in history.
- A per-repo, per-team record of which commits were defended and by whom —
  with privacy rules baked in (raw answers auto-purged after 90 days by
  default; individual score comparisons default OFF because they are
  HR-sensitive).

## Glossary

- **Pre-commit hook**: a script git runs before completing a commit; failing
  it cancels the commit.
- **LLM**: the AI model (large language model) that generates and judges
  questions.
- **Session**: one recorded attempt — the questions asked, answers given,
  scores, and metadata for a single commit attempt.
- **Ledger**: the team's central database of sessions; doubles as the
  enforcement record for CI.
- **Verification status**: every session is labeled honestly — `llm-verified`
  (AI-judged), `llm-unverified` (offline/degraded), `agent-unverified` /
  `unattended-unverified` (no human defended it).
